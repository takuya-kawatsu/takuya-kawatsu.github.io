8 台の DGX Spark による分散推論環境での vLLM 性能チューニング

DeepSeek-V4.1-Flash のデコードを、カーネル選択・one-shot RDMA all-reduce・通信待ちの L2 先読みで 2.3 倍にする

Performance Tuning of vLLM on an Eight-Node DGX Spark Cluster: A 2.3× Faster Decode for DeepSeek-V4.1-Flash through Kernel Selection, One-Shot RDMA All-Reduce, and L2 Prefetching during Communication

2026年10月

要旨

本稿では、CPU と GPU がメモリを共有する NVIDIA DGX Spark（GB10）8 台を 200 Gb/s の RoCE v2 で結んだ環境で、vLLM によるテンソル並列（TP=8）推論のデコードを高速化した結果を報告する。対象は 384 個のエキスパートを持つ Mixture-of-Experts（MoE）モデル DeepSeek-V4.1-Flash-1017（重み 510.3 GB）で、投機的デコーディング（DSpark、5 トークンの提案）を併用する。既定の構成では、GPU は 1 ステップの時間の 98〜99% でカーネルを実行しており、その多くを、テンソル並列で細分化されて低い実効帯域でしか動かない行列積と、1 ステップ 94 回の集団通信（all-reduce 88 回と all-gather 6 回）が占めていた。本稿では、(1) 重みだけを低ビットで持つ行列積カーネル（Marlin）への切り替えと、分割で生じたゼロパディングの削除、(2) CPU プロキシ型の one-shot RDMA all-reduce の vLLM への組み込み、(3) all-reduce と attention の待ち時間に、次に読む重みを別のストリームで L2 キャッシュへ読み込む先読み、(4) 投機ドラフトの固定費の削減、を行った。短いプロンプトでの単一ストリームのデコード（思考なし、温度 0、600 トークン）の 1 ステップは 60.6〜63.9 ms から 26.1〜27.7 ms に縮み（2.3 倍）、温度 0 の出力検査、並行時の正答、約 49 万トークンまでの needle 試験、HumanEval+/MBPP+、90 分の連続負荷のいずれでも、品質と安定性の低下は見られなかった。あわせて、CPU・GPU・NIC が同じ LPDDR5X を使う GB10 では、先読みの DRAM 読み出しと並ぶ RDMA all-reduce が 1 回あたり約 10 µs 延びることを単体測定で示し、通信と重ねる先読みが得になる条件を示す。

キーワード大規模言語モデル推論、vLLM、テンソル並列、Mixture-of-Experts、投機的デコーディング、RDMA all-reduce、L2 キャッシュ先読み、統合メモリ

Abstract. We accelerate tensor-parallel (TP=8) decoding in vLLM on eight NVIDIA DGX Spark (GB10) systems, whose CPU and GPU share one memory, connected by 200 Gb/s RoCE v2. The workload is DeepSeek-V4.1-Flash-1017, a 384-expert mixture-of-experts model with 510.3 GB of weights, served with DSpark speculative decoding (five draft tokens). With the default configuration the GPU was busy for 98–99% of each step, and most of that time went to TP-sharded matrix multiplications running far below memory bandwidth and to 94 collective operations per step (88 all-reduces and 6 all-gathers). We (1) switch to weight-only low-bit GEMM kernels (Marlin) and remove zero padding introduced by sharding, (2) integrate a CPU-proxied one-shot RDMA all-reduce into vLLM, (3) prefetch the weights needed next into the L2 cache on a separate stream while all-reduce and attention wait, and (4) cut fixed costs on the draft side. For short prompts (no thinking, greedy, 600 tokens) the single-stream decode step falls from 60.6–63.9 ms to 26.1–27.7 ms (2.3×), with no regression in greedy-output checks, concurrent correctness, needle tests up to about 490K tokens, HumanEval+/MBPP+, or a 90-minute soak test. We also measure that on GB10, where the CPU, GPU and NIC share one LPDDR5X memory, concurrent prefetch reads lengthen each RDMA all-reduce by about 10 µs, which we attribute, without direct verification, to the CPU, GPU and NIC sharing that LPDDR5X, and derive when overlapping prefetch with communication pays off.

1はじめに

大規模言語モデル（LLM）をエージェントとして用いるソフトウェア開発では、モデルがファイルの読み書きやテストの実行といったツール呼び出しを繰り返しながら、長い出力を生成する[1, 2]。利用者が一人の環境では、同時に処理する要求は主エージェントとサブエージェントを合わせて 1〜4 本程度であり、集約スループットよりも 1 本あたりのデコードの速さが待ち時間を決める。

NVIDIA DGX Spark は GB10 SoC を搭載し、CPU と GPU が 128 GB の LPDDR5X を共有する小型機である[3, 4]。1 台では数百 GB の MoE モデルを保持できないため、本環境では 8 台を RoCE v2（RDMA over Converged Ethernet。RDMA は remote direct memory access）で結び、vLLM[5] のテンソル並列（TP）[6] で 1 つのモデルを分割して実行する。小さいバッチのデコードでは、各 rank が毎ステップ自分の担当する重みをメモリから読み出すので、時間はメモリ帯域で下から抑えられる[7, 8]。さらに TP では層ごとに all-reduce が入り、ノード間の小さなメッセージの遅延が積み重なる。

本稿の対象である DeepSeek-V4.1-Flash-1017[9, 10]1 を vLLM の既定の構成で動かすと、投機的デコーディングの 1 ステップ（直前の確定トークンと 5 個の提案の計 6 行の検証と、ドラフトの生成）に 60.6〜63.9 ms を要した。後述のとおり、この時間はほぼすべて GPU 上の計算と通信であり、ホスト側の待ちは無い。したがって、高速化には GPU 上の時間そのものを減らす必要がある。本稿の貢献は次のとおりである。

  1. GB10 8 台での小バッチ MoE デコードの性能を、プロファイルと単体測定で分析し、時間の内訳と、帯域・通信から見た下限を示す（3 章）。
  2. 小さいバッチ向けの行列積カーネルを選び、TP 分割で生じるゼロパディングと形の不整合を解消する（4.1〜4.3 節）。
  3. CPU プロキシ型の one-shot RDMA all-reduce のコミュニティによる組み込みを upstream の vLLM に移植し、CUDA グラフの取り込み中だけ RDMA に回す 2 段階の有効化と毎ステップの fence を加えて、CUDA グラフでの使用と、障害時に壊れた出力を返さず停止する性質（fail-stop）を両立させる設計にする（4.4 節）。
  4. all-reduce と attention の待ち時間に次の重みを L2 キャッシュへ読み込む先読みを実装し、統合メモリでの通信との干渉を測って、適用の設計則を与える（4.5 節）。
  5. 投機ドラフトの固定費を、目標モデルの出力を変えずに削減する（4.6 節）。

これらは vLLM の Python 層への 9 件の修正（17 ファイル、追加 1,875 行・削除 27 行）と起動設定だけで実現しており、それぞれ環境変数で切り替えられる。短いプロンプトでの単一ストリームのデコードは 2.3 倍になり、品質と安定性の評価で低下は見られなかった（5 章）。

2対象システム

2.1ハードウェア

各ノードの GB10 は、Blackwell 世代の GPU（compute capability 12.1[11]、CUDA コア 6,144[3] の 48 SM（streaming multiprocessor）、L2 キャッシュ 24 MB[4]）と 20 コアの Arm CPU[3] を 1 つの SoC に載せる。両者は 256 ビット幅の LPDDR5X（128 GB、公称 273 GB/s[3]）を、ハードウェアのコヒーレンスを保って共有する[4]。ネットワークカードの ConnectX-7 も PCIe Gen5 x8 で SoC につながり[4]、DMA で同じメモリを読み書きする。以下では、compute capability 12.x の GPU をまとめて SM12x と書く。推論を止めた状態で測った 2 GiB のコピー（読み出しと書き込み）は 224 GB/s であった。

ConnectX-7 の物理ポート 0 は、OS からは PCIe Gen5 x4 の論理 NIC 2 つに見える。本環境ではこれを別サブネットの 2 本のレール（Rail A・B）とし、400G ポートを 2×200G に分けるブレイクアウト DAC（direct attach copper。1 本で 2 台、8 台で計 4 本）で、各ノードを MikroTik CRS804-4DDQ に収容した（図 1）。RDMA の基礎性能は、ib_write_bw（双方向、4 QP（queue pair））が 1 レールあたり 222.1〜222.8 Gb/s、両レール同時で 391.47 Gb/s、ib_write_lat（2 バイト）が 2.53〜3.06 µs である。PFC（priority flow control）と ECN（explicit congestion notification）は設定していない。DGX Spark は GPUDirect RDMA[12] に対応しない[13]ため、NCCL の GPU 主導の通信や NVSHMEM の IBGDA（InfiniBand GPUDirect Async）[14] は使えない。プロセスの制御（Ray・Gloo）は別の 10GbE 網を通す。構成を表 1 にまとめる。

2.2モデル

DeepSeek-V4.1-Flash-1017[10] は DeepSeek-V4 系[15]の MoE モデルで、40 層の各層が attention と MoE を持つ（表 2）。MoE は 384 個のルーティングされるエキスパートから上位 6 個を選び、共有エキスパートを併用する[16]。attention は DeepSeek-V4 の CSA（compressed sparse attention）を発展させた CSA2[9] で、系列方向に圧縮した KV を全ヘッドで共有し、indexer で選んだ上位のトークン[17]にだけ注意を向ける。CSA2 は KV と上位トークンの選択を層の間で共有し[9]、indexer と KV 圧縮器の少なくとも一方を持つのは 40 層のうち 8 層である。vLLM と FlashInfer では sparse MLA（multi-head latent attention）のカーネルで動く。残差の流れは mHC（manifold-constrained hyper-connections）[18, 19] で 4 系統に広げて層ごとに混合し、層 1 と 14 は参照専用の表 Engram[20] を引く。重みは、dense の線形層が FP8 e4m3（32×32 のブロックごとに 2 の冪のスケール）[21]、ルーティングされるエキスパートが MXFP4（32 要素ごとのスケール）[22, 23]で、合計 510.3 GB である1。

投機的デコーディング[24, 25]には、チェックポイントに同梱された DSpark[26] のドラフト（3 層、128 エキスパート）を使う。DSpark は目標モデルの 3 層分の隠れ状態を射影（main_proj）してドラフトの層に入れ、ドラフトの基底ロジットに、直前のトークンから計算する Markov 補正を加えて提案を 1 つずつ作る。本稿では提案数を k=5 とし、目標モデルは 1 ステップで 6 行（直前の確定トークンと 5 個の提案）を検証する。

2.3vLLM の実行構成

推論エンジンは vLLM の nightly（0.32.1rc1.dev36）で、FlashInfer 0.7.2[27] を含む。GB10（sm_121）で本モデルを正しく動かすため、upstream に出された 3 件の修正（PR。sparse attention のカーネルブロック、DSpark と CUDA グラフの組み合わせ、プロンプトのエンコーダ。付録 A）を加えた。TP=8 で各ノードに 1 rank を置き、Ray[28] でワーカーを起動する。V2 のモデルランナーを用い、デコードは CUDA グラフ[29] で再生する。KV キャッシュは FP8（fp8_ds_mla）、ブロックサイズは 64、最大文脈長は 524,288 トークンで、prefix caching を有効にした。

TP=8 では、各層の attention の出力と MoE の出力でそれぞれ all-reduce が要る。目標モデルの 80 回にドラフトの層などの分が加わって、1 ステップの all-reduce は 88 回になり、ほかに all-gather が 6 回ある（既定の構成。集団通信は計 94 回）。k=5 の検証 1 本あたりのメッセージは 60 KiB（6 行 × 5120 × BF16）である。また、統合メモリでは GPU 側の確保がそのままホストの空きを減らし、確保が失敗しないので、PyTorch のキャッシュアロケータが確保の失敗を契機にキャッシュを手放すこともない。長い prefill では文脈長に応じて大きさの変わる一時領域が再利用されずに積み上がり、ホストのメモリを圧迫するため、アロケータに expandable_segments を指定する。

3測定方法と既定構成の分析

3.1指標

投機的デコーディングでは、1 ステップで確定するトークン数（受理長）が出力の中身で変わる。そこで、デコードの時間 Tdec を、検証のステップ数 Nstep で割った 1 ステップの時間 tstep を主な指標とする。受理長 τ は確定したトークン数 Ntok から求める。

tstep = Tdec / Nstep,　τ = Ntok / Nstep(1)

1 本の要求の生成速度（tok/s）は次式で決まる。

生成速度 = τ / tstep(2)

カーネルを替えると数値誤差で温度 0 の出力が途中から分岐し、τ が変わる。実際、行列積のカーネルを Marlin に替えると、コードの続き書きの τ は 3.55 から 5.94 に変わった（5.2 節の構成 A と B。dense だけを Marlin にした構成でも 5.94）。式 (2) のとおり tok/s は τ にも比例するので、この変化はカーネルの速さと区別できない。そのため構成の比較には式 (1) の tstep を使い、tok/s は参考として併記する。Nstep は vLLM の /metrics が出す vllm:spec_decode_num_drafts_total の、要求の前後での差から得る。

3.2測定条件

tstep は、同じ 5 本の要求を 1 本ずつ流して測る（vllm-steptime.py）。内訳は、日本語の説明文（TCP のスロースタートと輻輳回避の違い）と Python コード（ISO 8601 の期間を秒に直す関数とテスト）を completions API（思考なしのテンプレートを手で適用）と chat API（思考を無効化）でそれぞれ 1 本、およびコードの続き書き 1 本（EOS を無視して 600 トークン）である。温度 0、最大 600 トークンで、ほかの要求が無い状態で head ノードから送る。以下で示す tstep の範囲は、この 5 本の最小から最大である。同じ構成を起動し直して測り直したときの差は、要求ごとに 0〜0.5 ms であった。温度 0 でも受理長は起動ごとに変わる（同じ要求で 2.82 と 2.93）。

時間の内訳は vLLM の torch profiler で取得した。帯域、FP8 GEMV、all-reduce、all-reduce と読み出しの干渉の単体測定は、推論を止めた状態で 8 台に同時に配るスクリプト（付録 B）で行った（コピーと cuBLAS の行列積の帯域は head ノードの値）。Marlin の行列積は推論を止めた head の 1 台で、L2 先読みは要求を流していない 1 台で測った。

3.3既定構成の時間内訳

図 2 に、既定の構成（5.1 節の構成 A）で、温度 0・192 トークンの要求を 1 本処理したときの 1 ステップの内訳を示す（プロファイラ下で 65.7 ms/step、素の状態では約 62 ms）。ルーティングされるエキスパートの行列積（DeepGEMM の FP8×FP4[30]）が 23.7 ms（36%）、dense の線形層（FlashInfer の CUTLASS[31] による MXFP8）が 18.2 ms（28%）、NCCL の集団通信（all-reduce 88 回・all-gather 6 回）が 13.8 ms（21%）、BF16 の線形層（4.3 節の wo_a など）が 5.6 ms（9%）を占めた。GPU が何らかのカーネルを実行していた時間の割合は 99.0% で（投機なしでも 98.4%）、CPU 側のオーバーヘッドやカーネル起動の待ちは律速になっていない。

投機なしでは dense が 46% を占め、MoE は 15% にとどまる。投機を使うと MoE が膨らむのは、検証の 6 行がそれぞれ別のエキスパートを選ぶためである。実際のルーティングを記録すると、1 層で読むエキスパートは 1 行なら 6 種類、6 行では 19.8〜22.7 種類、4 本を同時に検証する 24 行では 71 種類であった。

3.4帯域と通信から見た下限

テンソルの形と実際のルーティングから、各 rank が 1 ステップに読む重みを見積もると約 3.8〜4.1 GB になる。内訳は dense（attention・共有エキスパート・ルーター・mHC）が約 1.49 GB、ルーティングされるエキスパートが 1.86〜2.13 GB（1 個 2.35 MB × 1 層 19.8〜22.7 種類 × 40 層。ゼロパディングを含まない）、lm_head が 0.17 GB、ドラフトが約 0.3 GB である。メモリ帯域を W、rank あたりの読み出し量を V とすると、通信を除いても

tstep ≥ V / W(3)

であり、公称の 273 GB/s で約 14〜15 ms、実効の約 220 GB/s では約 17〜19 ms になる。既定の構成（A）の約 62 ms は、実効の帯域での下限（約 17〜19 ms）に対して約 3 割（28〜30%）の効率であった。なお A の経路はエキスパートの中間次元を 384 に切り上げて読むので、エキスパートの実際の読み出しは 2.5〜2.8 GB になる。

損失は二つの部分にあった。第一は行列積である。TP=8 で rank あたり 1.5〜9.2 MB（共有エキスパートの w2 から wq_a+wkv まで）に細分化された行列積が 1 ステップに約 300 本あり、既定のカーネル（FlashInfer の CUTLASS、起動時の自動チューニングは無効2）は推論中に約 60 GB/s しか出していなかった。同じ形を素朴な Triton の FP8 GEMV で回すと、1.5 MB の共有エキスパートの w2（145〜150 GB/s）を除いて 208〜240 GB/s が出る（表 3）。第二は all-reduce である。10〜60 KiB の小さなメッセージでも、NCCL[32] は 1 回 111〜155 µs（CUDA グラフ）を要した。RDMA の片道の遅延は 2.5〜3.1 µs であり、時間の大半はリングやツリーの段数と、その進行のしかたから来ている[33, 34]。NCCL のアルゴリズム、プロトコル、チャネル数を変えても縮まなかった。重みと投機を変えずに、行列積を帯域の上限近くで動かし、all-reduce を 1 回数十 µs にできれば、1 ステップは 21〜26 ms まで縮むと見積もった。

4.1小さいバッチ向けの行列積カーネル

Marlin[35] は重みだけを低ビットで持ち、活性は 16 ビットのまま計算する小さいバッチ向けの行列積カーネルである。原論文は FP16 の活性と INT4 の重みを扱い、vLLM の実装は BF16 の活性と FP8・MXFP4・MXFP8 の重みにも対応する。vLLM では起動引数で、dense の線形層と MoE の両方に選べる。ルーティングされるエキスパートには MXFP4 の W4A16 を、dense の線形層には MXFP8 の W8A16 を用いた。既定の経路（MXFP8 の CUTLASS、FP8×FP4 の DeepGEMM）は活性も FP8 に量子化して計算するのに対し、Marlin は活性を BF16 のまま扱う。

Marlin に切り替えると、1 ステップは 60.6〜63.9 ms から 41.3〜43.3 ms になった（1.5 倍）。dense だけを替えた場合は 53.2〜57.2 ms で、効果の大半は MoE 側にある。単体では Marlin の MoE は w13・w2 とも約 225 GB/s、dense の主要な形は 196〜218 GB/s で動き（表 3）、どちらもコピーの実測 224 GB/s に並ぶ。MoE ではタイルの設定を変えても差は 1〜4% で（dense はタイルを変えて測っていない）、どちらも専用のカーネルを書いて速くなる余地はほとんど無い。FlashInfer に実験的な機能として同梱されたカーネル集 b12x は、MoE（W4A8）だけを替えると 1 ステップ 42.2〜44.0 ms、dense（MXFP8）だけを替えると 42.4〜44.2 ms で、どちらも Marlin を上回らず、KV キャッシュの容量も減った（493 万から 329 万・419 万トークン）。

4.2TP 分割で生じるゼロパディングの削除

Marlin の経路でも、TP 分割で生じた形の端数がゼロパディングとして毎ステップ読まれていた。実際のルーティングから換算した MoE の実効帯域は 157〜172 GB/s で、単体の約 225 GB/s を下回っていたが、この差は次に述べるパディング（読み出し 1.33 倍）でほぼ説明できる。

エキスパートの中間次元。中間次元 2304 は TP=8 で rank あたり 288 になる。vLLM の Marlin 経路はこれを 128 の倍数の 384 に切り上げており、エキスパートの読み出しが 1.33 倍になっていた。Marlin の MoE カーネルは 64 の倍数で動く（w13 の出力 N と w2 の入力 K のタイルが 64）ので、切り上げを 64 単位の 320（1.11 倍）にした。1 ステップは 1.9〜2.8 ms 縮み、重みは rank あたり 7.7 GiB 減った。

w13 のゼロ行。この切り上げは、w13（出力 N）と w2（入力 K）に同じ中間次元を使うためのもので、64 の倍数にするために切り上げが要るのは w2 の K（288）だけである。w13 の N＝2×288＝576 はすでに 64 の倍数なので、読み込み時に w13 のゼロ行を捨てて 576 行に並べ直し、w2 は K＝320 のまま残す（表 4）。中間の活性は 288 列を書いたあと、w2 のゼロ行と掛け合わされる残り 32 列を毎回 0 で埋める。未初期化の値が NaN だと、0 との積も NaN になるためである。w13 の読み出しは 1 割減り、1 ステップは 0.6〜1.0 ms 縮んだ。

4.3形の合わない小さな行列

出力のグループ射影。attention の出力射影の前段 wo_a は 8 グループのグループ射影で、vLLM はこれをバッチ行列積（BMM）として扱う。SM12x には BMM 用の FP8 カーネルが無く、読み込み時に BF16 へ戻すエミュレーションに落ちて、重みを 2 倍読んでいた。TP=8 では rank あたり 1 グループなので、グループ射影は通常の行列積と同じである。この場合に限り通常の線形層として扱い、Marlin で FP8 のまま読むようにした。1 ステップは 1.2〜1.5 ms 縮んだ。

ルーター。MoE のルーター（BF16、384×5120）には、vLLM が Hopper（SM90）と SM100 に限って使う CuTe DSL の低遅延 GEMM[31] がある。このカーネルに必要なのは PDL（programmatic dependent launch）とスレッドブロッククラスタだけで、SM12x も備えているため、GB10 でも有効にした。ルーターは 1 層 33 µs から 24.5 µs になった（40 層で約 0.34 ms）。共有エキスパートの修正と合わせた 1 ステップの短縮は 0.1〜0.6 ms で、ルーターの分と同じくらいであった。共有エキスパートは補助ストリームでルーティングされるエキスパートと並行して動くため、活性の詰め直し（計 0.68 ms）が消えても 1 ステップはほとんど縮まないと考えられる。

4.4one-shot RDMA all-reduce

FlashInfer 0.7.2 は、b12x の通信ランタイム RoCEnante を実験的な機能として同梱している[36, 37]。これは、ピン留めしたホストメモリを GPU がその場で読み書きでき、NIC がそのメモリへ RDMA で書ける DGX Spark の構成を前提とした、one-shot の all-reduce と all-gather である（図 3）。各 rank はピン留めした領域を 1 つ持ち、GPU のカーネル（大きさに応じて 1〜8 CTA（cooperative thread array）。検証 1 本分の 60 KiB では 4 CTA）が入力を送信スロットへ書いて CPU のプロキシスレッドに知らせる。プロキシは 7 つの相手へ RDMA WRITE を出し（2 本のレールに分散）、GPU は相手から届いたデータと到着フラグを待って、rank の固定の順に FP32 で足す。全 rank が同じ順で足すので、結果は rank の間でビット単位に一致する。1 回のカーネル起動で完結し、NCCL のような段の往復を持たない。

単体の測定（表 3）では、1 行分の 10 KiB で 17.9 µs、検証 1 本分の 60 KiB で 39.4 µs（CUDA グラフ）と、NCCL の 111 µs・155 µs の 1/4〜1/6 であった。一方、1 MiB では 378.8 µs で NCCL（同じプロセスの eager で 251.3 µs）より遅い。

vLLM の upstream には、このランタイムの組み込みが無い。コミュニティによる vLLM フォークへの組み込み（PR #597[38]）は、大きさによる振り分け、CUDA グラフでの使用、rank 間の可否の投票、出力を返す rank での健全性の確認を備えていた。これに、フォークに出されてマージされずに閉じた PR #916[39] の RoCE の部分（生きている通信器すべての健全性の確認と単体試験）を合わせ、upstream の nightly と FlashInfer 0.7.2 の準備 API に合わせて移植し、次の点を変えた・加えた（差分は追加 1,133 行・削除 4 行）。

  • 振り分け。TP グループの all-reduce のうち 320 KiB 以下のもの、all-gather のうち 1 rank 分が 4 MiB 以下のものだけを RDMA に回し、それ以外は NCCL のままにする（フォークの上限は 2 MB と 16 MB）。上限は実測から、NCCL より確実に速い範囲に置いた（320 KiB では 138.4 µs 対 166.2 µs で RDMA が速く、1 MiB では 378.8 µs 対 251.3 µs で NCCL が速い。その間の大きさは測っておらず、表 3 の値を直線で結んだ見込みでは、両者が並ぶのは CUDA グラフで約 510 KiB、eager で約 450 KiB である）。中間の次元に沿った all-gather も最後の次元に平坦化して受け、Engram の表引きの集約も RDMA に載せる。
  • CUDA グラフとの両立（2 段階の有効化）。グラフの取り込み中に出た集団通信だけを RDMA に回し、取り込み前の暖機は NCCL で走らせる。JIT コンパイルを伴う暖機では rank の間で進み方がずれ、RDMA の待ちの上限（ポーリング 2,000 万回、約 20〜30 秒）を超えうるためである。取り込みの後は、eager の呼び出しも RDMA に回す。
  • 起動時の合意と自己試験。有効化の設定を全 rank で突き合わせる。Ray はドライバの環境変数をワーカーに setdefault で写すため、ノードの側の値が勝って食い違いうるからである。準備の各段階の成否を全 rank で投票し、本番と同じ経路で、3 つのデータ型と代表的な大きさ・形の all-reduce と all-gather の答え合わせを済ませてから配信を始める。
  • fail-stop の補強。待ちが上限を超えるとランタイムは使えない状態（毒化）になり、以後の出力は不定になる。フォークの、出力を返す rank がデバイスから結果を写した後にランタイムの健全性を確かめる処理だけでは、ほかの rank の失敗が NCCL 経由で出力に混ざる場合を見逃す。そこで、毎ステップのサンプリングの前に全 rank で 16 バイトの all-reduce（fence）を出すようにした。待ちが上限を超えた rank は、以後の eager の集団通信を起動せずに出力を 0 にして返し、fence も送らない。このため、どの rank が失敗しても、出力を返す rank の fence の待ちが上限を超えてそのランタイムが毒化し、写した後の確認で検出されてエンジンが止まる。逆に確認を通れば、全 rank が fence を送っており、それまでに各 rank が送った値は健全なランタイムで作られている。この性質は CPU 上の多プロセスの模擬試験で確かめたもので、実機での故障の注入は行っていない（6.4 節）。fence の費用（見積もりで GPU 時間約 18 µs）は tstep に表れなかった。

推論中のプロファイル（5.3 節の構成 C）では、目標モデルとドラフトの all-reduce は 1 ステップ 88 回（回数は既定の構成と同じ）で約 4.0 ms（1 回の中央値 42.5 µs、四分位 38.7〜47.4 µs）、all-gather は 10 回で約 0.3 ms で、1 ステップの通信は NCCL の 13.6＋0.6 ms から 4.38 ms に減った。1 ステップの短縮は 8.0〜8.4 ms であった。なお 320 KiB の上限は、検証 1 本の 60 KiB に対して 5 本分にあたる。6 本以上を同時に処理すると、目標モデルの all-reduce は NCCL に戻る。

4.5通信の待ちを使う L2 先読み

RDMA all-reduce を使っても、1 ステップには 88 回の all-reduce が残る（all-gather と合わせて 4.38 ms）。RDMA の all-reduce の間、GPU では少数の CTA がフラグを待つだけで、SM もメモリ帯域もほとんど使われていない。一方、all-reduce の直後に読む重みは層の構造で決まっており、その大きさ（次の層の wq_a+wkv で 9.2 MB など）は L2（24 MB）に収まる。そこで、待ちの間に次の重みを、主ストリームとは別の先読みストリームで L2 に読み込んでおき、直後の行列積が DRAM ではなく L2 から読むようにした（図 4）。通信の後に読む重みを通信と並行して先読みする考え方は PRESERVE[40] と同じである。

単体での効果。L2 に載った重みなら、行列積は 2.2〜3.9 倍速い（表 5。大きい行列ほど差が大きい）。wq_a+wkv（9.2 MB）は DRAM から 39.9 µs、L2 から 10.2 µs で、40 µs の待ちと並べて先読みすると合計が 25.2 µs 縮む。9.2 MB の wq_a+wkv では、PTX の prefetch.global.L2::evict_last と TMA（tensor memory accelerator）の cp.async.bulk.prefetch.L2[41] は命令を出し終えるだけで、直後の行列積は 32〜36 µs とほとんど速くならず、効いたのは通常のロード（ld.global.cg、L1 を通さない）で読んで捨てる方法だけであった。5.2 MB 以下の wq_b・共有エキスパートの w13・ルーターでは、TMA の先読みも通常のロードと同程度に縮めた（wq_b で 13.0 µs 対 12.9 µs）。窓では、最も大きい wq_a+wkv にも効く通常のロードを使う。

共有メモリの占有。Marlin は 1 CTA で SM の共有メモリをほぼ使い切る（約 99 KB）。先読みの CTA が残っている SM では Marlin の CTA が起動できず、先読みが次の行列積と重なると、かえってその行列積を遅らせる。

設計則。以上から、all-reduce と重ねる窓では、1 つにつき all-reduce が約 10 µs 延びることを前提に、それより明らかに大きく縮むものだけを使う。読む量は窓の長さに収め、窓を閉じる時点で主ストリームが先読みの全体を待ってから次の Marlin を始める。これに合うのは、MoE の出力の all-reduce の間に次の層の wq_a+wkv（9.2 MB。単体で DRAM から 39.9 µs、L2 から 10.2 µs）を読む MoE の窓（設定値 moe）であった。wq_b の後の attention の間に wo_a・wo_b（計 9.4 MB）を読む attention の窓（設定値 attn）は all-reduce と重ならず、代償は attention の側で払う。この読み出し（約 233 GB/s で約 40 µs）は、先読みが無いときの attention（wq_b の終わりから wo_a の始まりまで約 28 µs）より長く、wo_a はその終わりを待つうえ、attention の小さなカーネルも遅れる。窓の組み方が異なる構成で 1 層を取ったプロファイルでは、wo_a・wo_b は 24・31 µs から 7・7 µs になり、attention の小さなカーネルは計約 10 µs 遅れた。そこから見積もる短縮は 35 層で約 1.1 ms だが、実測の短縮は 0.2〜0.4 ms にとどまり、差の内訳は切り分けていない。attention の窓は、indexer や KV 圧縮器を持つ層では除く。その層では attention の中の行列積が、先読みに占められた SM を待つためである。

2 つの窓で、1 ステップは要求ごとに 0.5〜1.1 ms 縮んだ（MoE の窓が 0.1〜0.9 ms、attention の窓が 0.2〜0.4 ms。範囲の両端どうしでは 0.9〜1.0 ms）。出力が構成ごとに分岐する続き書きでは 0.5 ms にとどまる。先読みと並ぶ RDMA all-reduce は単体測定（表 6）で 1 回約 10 µs 延びるが、それを差し引いても 1 ステップは縮んだ。採用した窓の組み方での推論中の延びは、プロファイラで確かめていない（6.4 節）。

4.6投機ドラフトの固定費

DSpark のドラフトは、1 ステップに約 3.2 ms の固定費を持つ。このうち、受理の判定に影響しない部分を削った。

語彙を分担した Markov 補正。DSpark は提案の各位置で、基底ロジットに Markov 補正を足して argmax を取る。vLLM の実装では、各 rank が語彙全体（66 MB）の補正を 1 ステップに 5 回計算していた。各 rank が自分の受け持つ語彙 1/8 についてだけ補正後の最大値とその位置を求め、(値, 位置) の 16 バイトを all-gather して全体の argmax を選ぶようにした。全語彙の argmax と同じトークンを選ぶので近似ではない（同点は最小の語彙 ID を選ぶ）。速さは、補正を基底ロジットの上位 4,096 候補にだけ掛ける近似とほぼ同じで（RDMA all-reduce を入れた構成で 30.6〜32.3 ms 対 30.6〜32.4 ms）、その近似は 1 ステップを要求ごとに 1.1〜1.9 ms 縮めた。上位 128 候補に絞る近似は受理長を下げた（日本語の説明で 2.9 から 2.5）ため用いない。

FP8 の lm_head の写し。ドラフトの基底ロジットは、rank あたり 165 MB の BF16 の lm_head を毎ステップ読む（0.73 ms）。読み込み時に、32 要素ごとに 2 の冪のスケールを持つ MXFP8 の写し（83 MB）を作り、ドラフトだけがそれを読む。目標モデルは BF16 の lm_head のまま検証するので、受理の判定は変わらない。近い同点で別のトークンを提案することはありうるが、受け入れるかどうかは目標モデルが決める。

main_proj の分割。ドラフトの main_proj（FP8、78.6 MB）は全 rank に複製され、毎ステップ読まれていた（0.35 ms）。これを行の方向に TP 分割し、部分和を all-reduce 1 回で足すようにした。FP8 の写しと合わせて、1 ステップは要求ごとに 0.5〜1.0 ms 縮んだ。受理長は変わらなかった。

6考察

6.1残る時間と上限

D の時間の内訳はプロファイラで取っていないが、C の内訳（表 10）から見積もると、D の 1 ステップには次のものが残る。帯域の上限で動く MoE（C で 9.92 ms。D では w13 のゼロ行の削除で読み出しが減り、約 9.3 ms と見込まれる）、88 回の all-reduce を含む通信（C で 4.38 ms。D では MoE の窓で先読みと並ぶ all-reduce が延びる分と、main_proj の分割で増える all-reduce の分だけ長いと見込まれる）、dense、mHC、attention の小さなカーネルである。MoE と dense は、単体の測定でコピーの帯域に並ぶ速さで動いており、カーネルの改良で縮む余地は小さい。さらに縮めるには、読むバイトを減らすか、通信と計算の重ね方を変える必要がある。読むバイトの候補は、全 rank に複製している wq_a+wkv・ルーター・mHC 係数の分割や型の縮小（見込み 1〜3 ms）と、受理されそうにない検証行のエキスパートを読まない検証の打ち切り（見込み 1〜3 ms、未評価）である。vLLM の適応的な検証は、SM12x の indexer が可変長の検証に対応していないため、そのままでは使えない。このほか、Engram の層の射影（約 0.2 ms）、ルーターの行列積（1 層約 25 µs、コピーの帯域の約 7 割）、目標モデルの lm_head（0.74 ms、FP8 にするなら品質の確認が要る）が、それぞれ 1〜3% 規模で残る。

それ以上は構造の変更になる。層ごとの数十本のカーネルを持続カーネルにまとめ[47, 48]、all-reduce をカーネルの中のフラグ待ちで行えば、通信と計算を細かく重ねられる。見込みでは、同じ重みのままで 1 ステップ 21〜24 ms（A 比 2.6〜3 倍）に届くが、特定のモデルに専用の実装を持つことになり、保守の負担が大きい。重みを低ビットにすればエキスパートの読み出しは 3 割前後減るが、品質を優先する本環境の方針とは両立しない。

6.2統合メモリでの通信と計算の重ね合わせ

通信の待ちを使った先読みは、HBM を持つ NPU（Ascend 910B）の実機で効果が示されている[40]。ただし、先読みが通信そのものに与える影響は論じられておらず、L2 の容量を選ぶ設計空間の探索では、通信時間を一定の遅延とデータ量÷リンク帯域でモデル化している。このモデルでは、先読みは通信と重なる限り無償である。GB10 ではこれが成り立たなかった。先読みの読み出しと並ぶ RDMA all-reduce は、読み出しの量と開始の時刻によらず約 10 µs 延び、CTA を減らして読み出しを遅くしても、両方が終わるまでの時間は縮まなかった（16・8・4 CTA では読み出し単独より 7〜22 µs 長い）。CPU のプロキシ、NIC の DMA、GPU のフラグ待ちがすべて同じ LPDDR5X を通ることが原因と考えているが、メモリコントローラの側のカウンタで確かめてはいない。離散 GPU でも、計算と通信を重ねるとカーネルどうしがメモリや SM を取り合って遅くなることが報告されている[49, 50]。GB10 では、それに NIC の DMA とプロキシが加わる。したがって GB10 では、通信と重ねる仕事は「重ねても縮む量が、通信の延びより明らかに大きい」ものに限る必要があり、本稿ではこれを、窓ごとの短縮の見積もりと 10 µs 前後の延びの比較として設計に反映した。

6.3適用範囲

修正の多くは、vLLM の中でモデルに依存しない部分にある。エキスパートの中間次元の 64 単位化と w13 のゼロ行の削除は MXFP4 の MoE を Marlin で動かす経路、ルーターの低遅延 GEMM は SM12x のルーター、RDMA all-reduce は GB10 を複数台使う TP の通信に効く。L2 先読みは仕組みが汎用で、窓の登録だけがモデルの側にある。wo_a の線形化、共有エキスパートの読み込み時のパディング（DeepSeek-V4／V4.1 のモデル定義）、ドラフトの 2 件（語彙分担、FP8 の lm_head と main_proj の分割）は、DeepSeek-V4.1 と DSpark に固有である。RDMA all-reduce が有効になるのは、TP グループの rank が 2〜16 で複数ノードにまたがるときだけで、DBO（micro-batching）とは併用できず、FlashInfer に同梱の b12x の通信 API（API の版 1 と準備 API）に依存する。w13 のゼロ行の削除は MoE の LoRA を有効にすると使われない。FP8 の lm_head の写しは読み込み時に作るので、重みの入れ替えや sleep（レベル 2）では作り直されない。9 件は特定の nightly への差分なので、版を上げるたびに当て直しが要る。並行数については、RDMA all-reduce の上限（5 本）と先読みの上限（64 トークン）が、本稿の想定する 1〜4 本を覆っている。より大きな並行で使うなら、上限の引き上げと、先読みが NCCL の all-reduce と重なる範囲（6〜10 本）の得失を測る必要がある。

6.4妥当性への脅威

tstep は 5 本の短い要求を 1 回ずつ流した値で、反復による統計は取っていない（同じ構成を起動し直した測り直しの差は、要求ごとに 0〜0.5 ms）。0.5 ms 前後以下の寄与は、この差と同じくらいである。測定では思考を無効にしており、思考を伴う実際の利用での受理長と、エージェントが使う長さの文脈での tstep は測っていない。提案構成（D）の時間の内訳はプロファイラで取っておらず、表 10 は C までである。採用した先読みの窓の組み方での all-reduce の延びも、推論中には確かめていない。並行時の tstep も測っていない。基準の A は FlashInfer の自動チューニングを切った状態の値で、有効にした A は測っていない。A から B への短縮の一部は、この設定による dense の遅さに由来しうる。品質の評価は 1 つのチェックポイント（注 1）でのものである。

RDMA all-reduce は、待ちが上限を超えると推論を止める設計で、復旧には推論の再起動が要る。fail-stop が捕まえるのは RDMA ランタイムの失敗（待ちの時間切れ、プロキシの停止）である。出力を返す rank の GPU が RDMA 以外のカーネルで止まった場合は、vLLM の実行の時間切れ（300 秒）まで検知されない。出力を返さない rank が RDMA と無関係の理由でステップの途中に例外を出した場合の集団通信の組み違え（NCCL でも起きる）は、fence では検知できない。論拠はパイプライン並列を使わない（PP=1）生成モデルを前提にしている。また、NCCL より止まりやすい。1 ノードだけで実行時の JIT コンパイルが走るなどして rank の間のずれが約 20〜30 秒を超えると推論が止まり、約 0.5 秒の通信の途絶（QP の ACK の時間切れ 14、再送 7 回）でもプロキシは回復しない。運用では JIT キャッシュを全ノードで同じに温めておく。故障の注入（ノードの一時停止、レールの切断）による試験と、振り分けの上限を変えた比較は行っていない。

7関連研究

推論エンジンと小さいバッチの行列積。vLLM[5] と SGLang[51] は、KV キャッシュの管理とスケジューリングで LLM の配信を効率化する。小さいバッチのデコードでは重みの読み出しが支配的になることが、TPU での分析[7]やルーフラインのモデル[8]から知られている。重みだけを低ビットにする量子化[52, 53]と、それを小さいバッチで帯域の上限近くまで動かす Marlin[35] は、本稿のカーネル選択の前提である。FlashInfer[27]、DeepGEMM[30]、CUTLASS[31] は vLLM の既定の経路を構成する（CuTe DSL の低遅延 GEMM は Hopper と SM100 でだけ既定で使われ、本稿は SM12x にも広げた）。本稿の結果は、これらの既定の経路（MXFP8 の CUTLASS、FP8×FP4 の DeepGEMM）が TP=8 の小さな形と GB10 では帯域を使い切れず（自動チューニングを切った CUTLASS の dense で約 60 GB/s）、小さいバッチ向けの Marlin に替えるだけで 1 ステップが 19.3〜20.6 ms 縮むこと、そして Marlin に替えた後の行列積に残る損失の大部分が、TP 分割で生じるゼロパディングと形の扱い（その修正で合わせて 3.8〜5.9 ms）に起因することを示している。

集団通信。MPI の集団通信の最適化[33]以来、小さなメッセージでは段数の少ないアルゴリズムが有利とされる。NCCL[32, 34] は汎用だが、小さなメッセージでは段の往復の遅延が残る。ノード内では、TensorRT-LLM[54] や vLLM のカスタム all-reduce[55] が one-shot・two-shot の all-reduce をメッセージの大きさで使い分け、TensorRT-LLM の MultiShot[56] は NVSwitch のマルチキャストで段数を減らす。MSCCL++[57] は通信の抽象を推論向けに設計し直し、SiFAR[58] は one-shot all-reduce の前後の同期を固定費と捉えて削減している。GPU 主導の RDMA[14] は GPUDirect RDMA[12] を前提とするが、GB10 では使えない[13]。本稿の RDMA all-reduce は、統合メモリを前提に CPU のプロキシを介する RoCEnante[36, 37] と、コミュニティによる vLLM フォークへの組み込み（PR #597[38] と、マージされずに閉じた PR #916[39] の RoCE の部分）に基づく。#597 の組み込みは、大きさによる振り分け、CUDA グラフでの使用、rank 間の可否の投票、出力を返す rank での健全性の確認による fail-stop を備えていた。本稿はこれを upstream の nightly と FlashInfer 0.7.2 の準備 API に移し、実測に基づく振り分けの上限（320 KiB／4 MiB。フォークは 2 MB／16 MB）、中間の次元の all-gather の平坦化、取り込み中だけ RDMA に回す 2 段階の有効化、有効化の設定の突き合わせと自己試験、毎ステップの fence と失敗した rank での起動の省略を加えた。

通信と計算の重ね合わせ。T3[59]、FLUX[60]、TileLink[61] は、通信と行列積を細かい粒度で重ねる。Comet[62] は MoE のエキスパート並列での通信を重ね、NanoFlow[63] はバッチを分けて資源を同時に使う。PRESERVE[40] は通信の間に後続の重みと KV を L2 へ先読みする点で本稿に最も近いが、HBM の NPU を対象とし、先読みと通信の干渉は扱っていない。重ね合わせによる干渉は離散 GPU で測られている[49, 50]。本稿は、GB10 で先読みが RDMA の通信そのものを延ばすことを測り、窓の選び方に反映した。層を持続カーネルにまとめる手法[47, 48]は、6.1 節で述べた次の段階にあたる。

投機的デコーディング。小さなドラフトで提案し目標モデルで検証する方式[24, 25]は、複数のヘッド[64]、目標モデルの特徴量を入力とするドラフト（特徴量の水準での自己回帰[65]と、それを複数層の特徴の融合と直接のトークン予測に改めたもの[66]）、木構造の検証[67]、複数トークンの予測[68, 69]、検索による提案[70]へと広がった。本稿で用いた DSpark[26] は、並列のドラフト生成と軽量な逐次のモジュールを組み合わせる。本稿は方式そのものではなく、TP 環境でのドラフトの固定費（語彙方向の計算と複製された射影）を、目標モデルの出力を変えずに削る点を扱った。

統合メモリの計算機。CPU と GPU がメモリを共有する Grace Hopper では、データの置き場所と移動の性能が詳しく調べられている[71, 72]。GB10[3, 4] はこれを小型機に持ち込み、さらに NIC も同じメモリを使う。本稿の干渉の測定は、この構成での通信と計算の重ね合わせの特性を示す一例である。

8おわりに

8 台の DGX Spark で DeepSeek-V4.1-Flash-1017 を TP=8 で配信する vLLM について、デコードの時間を分析し、行列積カーネルの選択、TP 分割で生じるゼロパディングの削除、one-shot RDMA all-reduce の組み込み、通信の待ちを使った L2 先読み、投機ドラフトの固定費の削減を行った。短いプロンプトでの単一ストリームの 1 ステップは 60.6〜63.9 ms から 26.1〜27.7 ms になり（2.3 倍）、品質と安定性の検査で低下は見られなかった。最適化はすべて vLLM の Python 層への修正と起動設定で、upstream の改良を取り込み続けられる形にとどめている。GB10 では通信と計算の重ね合わせは無償ではなく、先読みと並ぶ RDMA の通信が 1 回 10 µs 前後延びることも分かった（CPU・GPU・NIC が同じ LPDDR5X を使うことが原因と考えているが、確かめてはいない）。残る時間の大半は帯域の上限で動く行列積と all-reduce で、さらに縮めるには、読むバイトの削減か、通信をカーネルの中に取り込む構造の変更が要る。

付録 B測定の道具

  • vllm-steptime.py：3.2 節の 5 本の要求を 1 本ずつ流し、/metrics の投機のステップ数の差から tstep と τ を出す。
  • vllm-needle.py：乱数の単語列の深さ 37% に番号を埋め、初回（prefix cache を外す）で prefill の速さと正誤を、2 回目（同じ本文に別の質問）で長い文脈でのデコードの速さを測る。
  • vllm-greedy-diff.py、vllm-concurrency-check.py：5.5 節の温度 0 の出力検査と並行時の正答。
  • vllm-soak.py：一定の並行数で要求を流し続け、1 分ごとの集約スループット、エラー、受理長を記録する。
  • spark-bench/：単体測定の道具。メモリ帯域、FP8 GEMV、NCCL と RDMA の all-reduce の遅延、all-reduce と読み出しの干渉は、推論を止めて 8 台に同時に配って実行する。Marlin の MoE と dense は推論を止めて、L2 先読みは推論を止めるか要求の無いときに、それぞれ 1 台で vLLM のイメージの中で測る。ルーティングされたエキスパートの種類数は、--enable-return-routed-experts を付けて起動した推論に要求を流し、推論コンテナの中で数える。干渉の測定スクリプト（roce-contention.py）がそのままで測るのは 9 MiB・48 CTA × 8 warp の組と開始の遅延で、表 6 の 4 MiB と 16 CTA × 4 warp の行（と表 6 の注の 8・4 CTA）は、同じスクリプトの読み出しの組（CTA 数・warp 数・量）を替えて測った。
